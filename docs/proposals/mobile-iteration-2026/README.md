# Android 独立端迭代建议（参考 dsh-Go）

本文是**建议稿**，不是执行授权，也不改变任何现行合同。条目被采纳后由维护者分配 `ITER-###` 并写入 [plan.md](../../../plan.md)；在那之前，文中的"建议做法"不代表已批准范围。能力状态、真机证据与发布门槛仍以[追踪基线](../../reference/REQUIREMENTS_TRACEABILITY.md)和 [ITER-009](../../../plan.md#iter-009) 为准。

## 0. 为什么看 dsh-Go

dsh-Go 是把 DeepSeek Harness 装进手机的第三方 Android/iOS 应用（AGPL-3.0，`sdk/`、`examples/` 为 MIT），已公开发布 APK 并有真实用户反馈循环。它的价值不在功能清单，而在**把移动端独有的一批问题写成了可复用的判断**：流式渲染怎么不闪、短视口和键盘怎么让位、审批怎样和"任务"绑定、哪些"保活"其实不是保活、发布号怎么不打架。

取证口径：以下引用固定到 `ccch1mneyyy/dsh-Go` 的 `f2d589c4a7f415f0d0a9f3c3a1a57a94ac0e11f4`（2026-11-25）。本文只借设计与判断，不复制其代码或素材；若后续需要移植具体实现，应按[架构与参考学习](../../reference/ARCHITECTURE.md#reference-learning)的规则登记来源、固定提交与许可影响（本项目为 AGPL-3.0-or-later，与其同族，但仍须逐文件记录）。

## 2. 先修一致性：四处文档与实现的偏差

这一批不改产品行为，只让"文档说的"和"代码做的"对上。它们的共同风险是**让后续验收失去判据**。

| 项 | 现象 | 建议 |
|---|---|---|
| Shizuku 口径 | [ADR-022](../../reference/adr/ADR-022-mobile-runtime-access.md) 的 P2 行写"未接入"，但原生已把它作为 root 之后的第二 transport 并上报 `shizuku` 字段；运行面板文案写"当前安装包尚未集成 Shizuku"，同一文件的开关判据却允许 Shizuku 解锁设备开关 | 三处统一为一个口径。反射调用说明"未引入 SDK 依赖"成立，但"未接入"作为能力描述已不准确 |

| 过期记录 | [plan.md](../../../plan.md#iter-009) 仍写"角色区域增至 64dvh"，现实现已改为舞台裁切方案（舞台 `clamp(280px, 42dvh, 480px)`、角色盒更高并被裁）；Android 工作流注释称 79 项仪器用例，实际 90 项 | 更正为现实现数值与当前用例数；后者建议改为不写死数字的表述，避免每次加测都要改注释 |

## 3. 第一批：对话体验（用户每天都在碰）

### 3.1 流式 Markdown：稳定前缀先排版，只修补未完成的尾部

**问题。** 现实现流式期间走纯文本分支，收到完整回复后才整体换成 Markdown。用户看到的是：一段没有排版的代码块和列表，结束时整块重排、位置跳动，长回复尤其明显。

**dsh-Go 的做法。** 显示管线与原文严格分离（复制、分享始终用原文），流式时只修补**最后一个未完成的块**：未闭合的粗体、斜体、删除线、行内码先替它闭合；半截链接按链接显示；半截图片整块压住不显示；表格等分隔行完整才出现；单独的行标记先压住。它对未闭合的块级公式明确选择"显示源码直到闭合"，而不是自动补全——因为半截公式渲染出来会反复跳。

**建议。** 分两步，第一步不引入新解析器：

1. 把回复按空行切成"完整块"与"尾部块"。完整块走现有 `renderMarkdown` 并缓存，尾部块保持纯文本加光标。这一步就能消掉"结束时整块重排"。
2. 在尾部块上补最小修补集：未闭合的行内标记、半截链接、围栏语言名。表格与公式的修补留到确有需求时。

**验收。** 逐项反例（先写反例再实现）：回复到一半时粗体不再露出 `**`；表格在分隔行到达前不出"一堆竖线"；结束瞬间不产生可见的位置跳动。**不宣称**：不把修补当解析器正确性，不改变原文。

**依赖与风险。** 纯前端，位于 `plugins/surfaces/proactive-ui`，须按两仓配对 PR 交付。风险是修补规则与真解析器不一致时"显示与复制不同"，因此必须守住"显示可容错、原文不动"。

### 3.2 用"数重建次数"替代"测帧时间"

**问题。** 流式性能目前没有可回归的判据，只能靠真机手感；WebView 的帧时间在 CI 里不可靠。

**dsh-Go 的做法。** 它在行模型里留了一个派生计数器，测试直接断言：流式期间只有正在写的那一行重建、已完成的行重建 0 次、行模型派生 0 次。它把这条写进了架构文档的"聊天流式性能契约"，并列出**缓存失效面的显式清单**——行构建层读到但不随行对象变化的东西，要么清空缓存表，要么挪进各自的 build。

**建议。** 在手机对话气泡上包一层计数探针（渲染次数、Markdown 重算次数），用测试断言"收到 N 个增量时，已完成内容的重算为 0"。这项成本约一天，是后续所有流式优化的地基。

### 3.3 失败原因分类，而不是一句话硬编码

**问题。** 现在的失败文案是按场景写死的中文句子（例如授权续跑失败、观测中断），无法区分"网络断了""凭据失效""被前台规则拒绝"。

**dsh-Go 的做法。** 固定失败原因枚举（权限、网络、超时、认证、提供方限额、运行时、完整性、不支持、其他），**用户只看到一句，分类只进日志与测试**。

**建议。** 在手机端错误路径上引入同构的有限枚举，UI 保持一句话，诊断与测试读分类。这是诊断包（§5.1）的前置。

### 3.4 回复中想补充信息时，允许"排队一条"

**问题。** 回复进行中再发送会被准入拒绝（`REPLY_IN_PROGRESS`），用户唯一的表达方式是停止后重发，代价是丢掉已生成的内容。

**dsh-Go 的做法。** 四种发送语义：立即、在下一步并入（steer）、等本轮结束（queue）、先停再发。入口是长按发送键。它对"弹层跨越状态变化"还有一个值得抄的防御：打开弹层时捕获草稿、会话、连接世代与引用的快照，用户选完逐项核对，任一不符就静默放弃发送。

**建议。** 只做最小的 `queue`：允许挂一条待发消息，本轮正常结束后自动发出，界面上明确标"本轮结束后发送"，并允许撤回。`steer` 需要执行侧支持，不在本批。**不宣称**：排队不等于插话，也不改变"停止只停止、不回滚"的既有语义。

**依赖。** 触达 `apps/web/src/mobile` 的准入与 `packages/api-client` 的控制器状态，属于跨包改动，应单独立项。

### 3.5 过程与思考的呈现（可选）

**问题。** 手机端只有一个工具活动标签，契约里的 `reasoning_delta` 没有展示；一轮里做过什么，用户看不到。

**dsh-Go 的做法。** 折叠单位是**轮**而不是消息：正常结束的轮收成一行摘要（几件工具、几条消息），点开按原样展开；**被停下或出错的轮不收**，让用户一眼看到停在哪一步。回合脚注按固定顺序舍弃字段（先丢 tokens，再丢步数，时长永远在）。

**建议。** 先只做"轮结束后一行摘要 + 可展开"，不做完整轨迹页；这是"看得见做过什么"的最低成本版本。用户明确表示不关心过程时，不强行展开。

## 4. 第二批：可发现性与信息架构

### 4.1 设置索引单一来源 + 三道测试

**问题。** 手机设置分散在三处：顶栏齿轮、首页卡片、设置弹层；弹层内又分固定分类与运行面板内的六个分页。改一个名字要改多处，且没有"搜一下"的入口。

**dsh-Go 的做法。** 一张 `SettingSpot` 表（页面、行、标题、同义词、可用条件、频率）作为唯一来源：行组件从表里取标题，页面与索引不会漂移；搜索、深链、使用说明都读同一批条目。配套三道测试：页面里每行都必须带索引项（例外进白名单）、索引自身自洽（id 唯一、无孤儿页、同义词非空）、使用说明里的路径必须等于某个索引项的面包屑。

它的落地顺序值得照抄：**先索引和搜索，再重组首页，最后做就近设置**。前两步不动物理布局就能解决"找不到"。

**建议。** 第一步只做索引表 + 自洽测试，不动布局；第二步加搜索（归一化、同义词含旧名、不可用项也列出并写明条件）；第三步才重组首页。搜索结果的落点要单独定：直接进目标页，返回回搜索结果，目标行高亮**只改底色不改行高**（否则会推动布局）。

**风险。** 改动面宽（每个设置行都要挂 id），且位于插件仓。收益是把"文档、搜索、深链、AI 回答里的位置"统一到一处。

### 4.2 会话列表：分组、筛选、全量搜索

**问题。** 首页会话卡只显示前 3 条，弹层里的搜索只过滤已加载列表（该缺口已在计划中记录）。

**建议。** 按天分组（今天、昨天、本周、更早，用排序键而非最后消息时间的日界）；筛选按"运行中、待确认"；搜索在翻页拉齐后才宣称覆盖全量，否则在结果里明确"仅已加载"。**不宣称**：筛选不改变未加载部分的判断。

### 4.3 断点与短视口：需要一次几何复核

**问题。** 现实现里"短视口收起角色"由 `pc-viewport--short` 的类规则实现，而移动 Material 3 的两栏布局写在 `min-width: 600px` 媒体查询内、选择器带 `[data-design-system][data-platform]` 两个属性。后者特异性更高且位于样式表更后。对横屏手机（例如 915×412：宽够两栏、高低于短视口阈值）而言，两条规则同时成立，**两栏规则可能胜出，使角色不被收起**。这与移动工程说明和设计规范里"短视口收起角色"的描述不一致。

**dsh-Go 的做法。** 它按**最短边**分类：高度低于阈值时一律当手机单列，不论宽度；理由写得很具体——412 高减去状态栏、顶栏、输入条只剩几行，键盘再占一半，两栏会让每栏只剩一条缝。

**建议。** 先补一个几何测试覆盖横屏手机与分屏窗口（量舞台是否隐藏、内容列数、输入条是否在可见视口内），再按结果修选择器或调整判定顺序。**结论以测量为准**；本文只指出需要复核的位置，不下"已损坏"的结论。

### 4.4 本地化：先立规矩，不搬整套工程

**问题。** 现实现无 i18n 依赖，文案全部硬编码中文。

**dsh-Go 的做法。** 分片文案合并、生成物入库、CI 用"重新生成一次再比对"防手改，另有只校验不写回的增量翻译工具。

**建议。** 现阶段不建议搬这套重工程：没有第二语言需求时，收益主要在"文案可被审阅"，成本却贯穿构建链。更划算的是先立两条规矩：文案集中在单一模块（不在组件内散落字面量）、新增文案必须可被搜索。等确定要做第二语言，再按分片方案迁移。

## 5. 第三批：可靠性与运维

### 5.1 手机端诊断包（分层 + 脱敏 + 给 AI 看的那一份）

**问题。** 手机端没有诊断出口。用户报"发不出去"时，只能靠描述；备份导出是业务数据，不是排障事实。

**dsh-Go 的做法。** 一个 zip 里分文件（摘要、设置、系统输入法证据、崩溃分类、原生证据、引擎日志），每条字符串都过脱敏（剥离终端控制符、逐行截断、启动令牌、认证头、键名赋值、私钥整块、已知前缀保留前几位让人看得出是哪类密钥）。另有两道边界：自动分析只发**无内容的事实**（且必须匹配白名单字符集与长度）；手动导出保留更宽的收集与同意边界。给引擎里 agent 读的那份**有硬上限**（十几行、16 KiB），理由是"超过这个成本的诊断文件已不值得读"。文档里同时写明：自动打码不能当保证，分享前自己检查。

**建议。** 分两步：先做"分层 + 逐行脱敏 + 用户预览再分享"，再做"给模型看的摘要"。脱敏规则必须有单测（含反例：不该被打码的 `max_tokens` 之类）。**不宣称**：导出成功不代表已脱敏干净，UI 上必须写明。

### 5.2 构建号改为可排序序列

**问题。** `versionCode 1` 固定。开发包、内测包、候选包之间无法区分先后，覆盖安装与回退都没有依据；第三批的签名内测会直接撞上这一点。

**dsh-Go 的做法。** 构建号编码时间（年偏移 + 月日时分），固定时区而非本机时区，附带解码与校验入口；理由是"后构建的永远大于先构建的，时区或夏令时不能让序列倒退"。

**建议。** 采用同构方案，并补一个校验入口。这是零成本的确定性收益，不涉及任何产品行为。

### 5.3 更新检查（不引入特权安装）

**建议。** 只做"版本可见 + 检查更新 + 引导手动安装"，并区分"检查成功但无更新"与"检查失败"，节流用两个间隔（成功一个较长间隔、失败较快重试，避免离线用户每次开 App 都撞一次）。**不建议**做特权安装：那会把自更新推进 P2/P3 的授权面，与现有能力分级冲突；Aervox 的 APK 不含运行时资产，增量补丁的收益也不成立。

## 6. 明确不建议借鉴

| dsh-Go 的做法 | 为什么不适用 |
|---|---|
| 内置 Linux 运行时（PRoot、分层资产、路径缓存、原件库） | Aervox 无运行时资产，冷启动问题根本不同 |
| 前台服务 + 唤醒锁 + 系统重建恢复；iOS 静音音频与定位保活 | 与"离开前台即取消"的现行合同相反。若将来要加，只借它的判断——保进程、获执行时间、重连、恢复引擎、继续对话是五件事，通知还在不能证明任务在跑——而不借实现 |
| 实时活动 / 灵动岛 | 依赖常驻通知与厂商白名单；dsh-Go 自己的真机记录显示国行部分系统对第三方一律不放行 |
| 原生插件协议与视图组件树 | 依赖其宿主。可参考的是它的预算与降级原则（视图超限截断、根坏整块降级），不是协议本身 |
| 桌面图标多套、主题包声明式 schema、宠物悬浮窗 | 与现有 Material 3 品牌基线和 WebView 内角色方案重叠，收益不抵维护面 |

## 7. 建议的落地顺序与挂接

| 批 | 内容 | 主要位置 | 前置 |
|---|---|---|---|
| 顺序 0 | §2 四处一致性修正 | 文档 + 原生 + 工作流注释 | 无（可立即做） |
| 顺序 1 | §3.1 流式 Markdown、§3.2 重建计数探针 | 插件仓界面 | 两仓配对 PR |
| 顺序 2 | §5.2 构建号、§3.3 失败分类 | 原生构建 + 手机端错误路径 | 无 |
