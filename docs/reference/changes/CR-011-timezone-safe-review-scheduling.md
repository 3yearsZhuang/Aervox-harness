## 变更

- **原因**：v1 调度通过增加固定 24 小时计算“若干天后”，跨夏令时会让本地到期时间偏移，汇总也无法区分今日到期与历史逾期。
- **关联能力与需求**：`CAP-006`、`FR-REV-001`、`NFR-I18N-001`。
- **时区来源**：API Client 运行时配置是学习操作的统一 IANA 时区来源，默认读取系统时区；每次创建复习项时将其保存为 `timezoneSnapshot`。
- **v2 调度**：在完成时区中增加本地日历天并保留墙上时间，再转换为 UTC `dueAt`；跨 DST 的一天允许是 23、24 或 25 小时。
- **兼容**：已有 v1 复习项保持原 `dueAt`，不批量重算；用户完成旧项后生成带时区快照的 v2 下一项。
- **逾期**：本地当日零点以前到期且仍为 active 的项目计入 `overdueCount`；当日零点至查询截止时间的项目计入 `dueTodayCount`。逾期项目不复制，完成后从实际完成时间按 v2 重新调度。

## 验证与回滚

- **验证**：单元测试覆盖 DST 春季/秋季切换（23/25 小时自然日）、南半球 DST、无 DST 时区、跨时区调度和墙上时间保持；API 集成测试覆盖逾期不重复创建活动项、从实际完成时间重新调度（非原到期时间）、时区快照保存与跨时区更新、汇总接口按时区区分今日到期与逾期、非法时区及租户隔离。覆盖 `AC-FR-REV-001-03`。
- **回滚**：停止写入 `timezoneSnapshot` 并恢复 v1 固定时长调度；保留已生成的 UTC `dueAt`，不删除或重算历史复习项。
