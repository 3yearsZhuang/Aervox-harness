## 变更

- **变更原因与证据**：`CAP-003` 已有题组创建、会话作答和服务端判定实现，但追踪矩阵仍缺少题目选择、快照、会话状态、重复提交和不可验证判定的可验收边界，不能据此将能力标记为 Ready。
- **关联能力与需求**：`CAP-003`、`CAP-004`、`FR-PRC-001`、`NFR-REL-001`、`SEC-TEN-001`。
- **当前行为 / 目标行为**：保留现有“活动题目按创建顺序选取、3～5 题、会话保存题目 ID、服务端确定性判题”的范围；在 SRS 中明确异常、重试、完成和隔离规则，并建立稳定的验收与测试 ID。
- **范围外**：AI 生成题目、主观题人工批改、学习路径自适应、跨设备离线同步，以及改变复习调度算法。

## UX、API、数据与安全影响

- **UX**：题目不足时展示不可开始原因；已结束会话禁止继续提交；网络重试使用同一 `Idempotency-Key`，客户端按原响应恢复，不重复展示进度变化。
- **API**：不新增端点；明确创建会话、提交作答、查询报告和结束会话的返回与错误语义。`POST /v1/questions/{questionId}/attempts` 的幂等键统一位于 `Idempotency-Key` 请求头，并区分首次写入 `201` 与幂等重试 `200`。
- **数据**：会话的题目 ID 列表是开始时快照；原始 `QuestionAttempt` 不可修改；相同幂等键不得形成第二条作答或第二次掌握度/复习调度更新。
- **安全与隐私**：所有会话、题目、作答和报告均按工作区与数据主体隔离；跨租户资源统一返回 404，不泄露资源存在性。

## 验证、回滚与决策

- **测试与验收影响**：新增 `TC-API-PRC-001`、`TC-INTEG-PRC-001`、`TC-E2E-PRC-001` 追踪；本次以 contracts build 重新生成 `openapi.json` 并以 `openapi-contract.test.ts` 锁定作答幂等请求头与 `201/200` 响应语义；实现阶段需覆盖题目不足、快照稳定、重复提交、已结束会话和跨租户访问。
- **迁移与回滚**：本次仅补充规格与追踪，不含运行时迁移；若评审拒绝，恢复 SRS 和追踪矩阵中本 CR 的规则与引用即可。
- **决策**：Review Candidate。待产品、设计、工程和 QA 对会话恢复文案、错误码与 E2E 路径留痕后，方可随 `CAP-003` 进入 Ready 评审。
