## 1. 变更背景与驱动因素

### 1.1 范式迁移的窗口期

主流 AI 应用（ChatGPT 桌面端 Work 形态、Codex、ZCode 等）已经把一套交互范式变成了大众习惯：**左侧会话与项目导航 + 中央对话流 + 输入框模式选择器（模型 / 访问级别 / 项目上下文 / 附件）+ 任务与插件中心**。从这些应用迁移过来的用户，带着这套肌肉记忆来到思隅时，面对的是「桌宠 + 视觉小说 + 工作台」的三态混合——产品个性鲜明，但第一小时的认知成本偏高。降低迁移用户的上手难度，等于把这扇门修宽。

### 1.2 现状差距（基于现有工作台组件的事实核对）

现有 `AervoxWorkbench` 是「NavPill 导航 + 对话控制台 + 侧卡」布局，对照熟悉范式存在三处结构性缺口：

1. **无会话列表侧栏**：历史会话虽有「回看完整对话」入口，但没有可切换、可检索、可分组的会话导航；多会话用户无法像在熟悉范式中那样管理对话资产；
2. **无统一任务中心**：定时任务散落各处（日记计划、复习排期、番茄钟、主动智能规则各属不同设置分区），没有一张「我的 Agent 在替我做什么」的统一视图——而这恰是熟悉范式里「定时任务」入口的心智预期；
3. **无项目上下文绑定**：会话不能挂在项目/资料/知识库之下，上下文与资产（学习材料、收藏、主动 projects 推断结果）之间缺少用户可控的组织层。

### 1.3 不做什么（定位声明）

熟悉范式的**承接不等于定位的改变**：思隅的差异化（桌宠陪伴、主动智能、学习闭环、local_only）是护城河，不是要被替换的旧皮。本 CR 明确两条红线：

- **不做编码代理**：终端执行、代码 diff 视图、仓库级 agentic coding 是 Codex/ZCode/Claude Code 的主战场，与「陪伴 + 学习」定位无协同，明确出圈；
- **不引入整套第三方聊天前端**替换 `ConversationConsole`：那会孤儿化主动智能、桌宠、人格管线与安全门禁等全部差异化投入（评估详见 §3）。

## 2. 设计裁决：原生交互壳 + 插件插槽

沿用 CR-033/CR-034 确立的归属框架（承诺与可用性归内核，场景与内容归插件）：

1. **标准模式交互壳是原生能力**——会话导航、项目上下文、任务中心是产品的前门与状态骨架（会话列表的选中态、导航布局与工作台上下文深度耦合），且「上手不迷路」与 CR-034 的「断网不哑」同属产品承诺，不依赖可选扩展；
2. **壳内的内容与扩展走既有插件面**——侧卡、设置页签、消息动作、输入框扩展已由 CR-006 的插槽体系（`sidecards:widgets`、`settings:tabs`、`composer:*` 等）承载；第三方「任务类型」「面板」类需求以插件形式进入插槽，不为它们新开壳级契约；
3. **双形态一致性**：标准模式与陪伴模式共享同一套后端契约与状态（会话、人格、主动智能、插件运行时），切换的是信息架构与表现密度，不是两套应用；桌宠在任何模式下经托盘/悬浮常驻可达。

## 3. 开源方案评估：借范式，不借代码

对「有没有成熟的可以直接使用的开源方案」的回答是：**有成熟的范式参照系，没有可以直接嵌入的方案**。

| 候选 | 定位 | 评估结论 |
|---|---|---|
| LibreChat / Open WebUI / LobeChat 等聊天前端 | 多模型会话管理、插件生态 | 范式与信息架构的最佳参照（会话分组、模型选择器、导入导出约定）；但作为整套前端嵌入会与思隅的 SSE 回合流、工具审批卡、VN 元素、人格与主动智能体系全面冲突，且各项目许可证条款（品牌保留、AGPL 系传染性）需逐项复核，引入即背长期维护面 |
| OpenHands / Cline / Aider 等编码代理 | 终端与代码仓库操作 | 与 §1.3 出圈红线冲突，仅借鉴其任务态与 diff 呈现的产品思路，不引入 |
| 各家交互约定本身 | 无代码 | 真正「可直接使用」的部分：会话分组与重命名、输入框模式选择器、⌘K/⌘N 快捷键约定、首次引导节奏——以设计规范形式吸收进标准模式 |

结论：**采用范式与约定，不引入代码库**。实现载体是 `packages/ui` 内的现有组件体系（`useAervoxApi`、`api-client` 合同、扩展插槽），增量全部是自有组件的组合与排布，许可证风险为零。

## 4. 终局形态：双形态信息架构

### 4.1 标准模式（新增）

```text
┌────────────┬──────────────────────────────┬────────────┐
│ 导航侧栏    │  对话流（ConversationConsole） │ 上下文卡片区 │
│            │                              │            │
│ ◇ 新对话    │  … 与陪伴模式共用回合管线 …     │ 项目资料     │
│ 会话/分组   │                              │ 学习目标     │
│ 项目       │  [输入框：模型 ▾ 访问级别 ▾     │ 主动动态     │
│ 任务中心    │   附件 ⌘K 快捷指令]            │ (插件插槽)   │
│ 插件中心    │                              │            │
```

### 4.2 形态切换

- 陪伴模式（现状工作台 + 桌宠 + VN 元素）与标准模式（本 CR）共享会话、人格、记忆、主动智能与插件运行时；切换是布局与表现密度的切换，设置持久化；
- 桌宠在标准模式下经托盘与悬浮窗常驻，主动事件（CR-032 直推）双形态一致送达；
- 新用户默认路径可配置：从其他 AI 应用迁移而来的用户在首次引导中可选择「以标准模式开始」（与既有 OnboardingFlow 衔接）。

## 5. 设计支柱

### 5.1 P1 会话导航与模式选择器

会话列表侧栏：会话枚举、分组/置顶/重命名、跨会话检索；输入框模式选择器聚合既有概念（模型预设——含 CR-034 的降级层级标识、完全访问级别、项目上下文、附件），把散落的设置前置到零成本触点。

### 5.2 P2 项目上下文

会话可绑定项目；项目聚合三类资产：学习材料/知识条目（衔接既有学习与收藏能力）、该项目的会话集合、该项目相关的主动智能对象。与主动智能 projects（自动推断）的关系：自动推断结果作为项目候选呈现，用户确认后转为显式项目——推断是起点，不是终态。

### 5.3 P3 任务中心

把散落的定时能力（日记计划、复习排期、番茄钟、主动智能规则与冷却状态）聚合为统一视图：「Agent 正在替我做什么、下次何时、结果如何、如何调整」。只读透传既有调度状态 + 入口跳转到各自设置分区，不重造调度语义。

### 5.4 P4 迁移友好设施

OpenAI 兼容模型配置已备（CR-034 补本地端点）；增加：其他应用会话导出格式的导入器（按主流应用的导出 JSON 逐个适配，首版选一家）、快捷键约定对齐（⌘K 命令面板、⌘N 新对话）、术语表对齐（会话/项目/任务/插件四大名词与主流应用一一对应）。

### 5.5 P5 双形态一致性

标准模式不是平行应用：同一会话在两形态下呈现一致的历史与状态；插件运行时、主动智能、人格管线在两形态下行为完全一致；桌宠的主动表现（动画 + 气泡）在标准模式下照常工作。

## 6. 当前行为 vs 目标行为

| 维度 | 当前行为 | 目标行为 |
|---|---|---|
| 会话管理 | 回看完整对话（单会话回溯） | 会话列表侧栏：切换、分组、检索 |
| 定时任务 | 分散于各设置分区 | 任务中心统一视图（只读透传 + 跳转） |
| 项目上下文 | 无显式绑定；projects 自动推断 | 会话绑定项目；推断结果转显式项目 |
| 模式选择器 | 模型/访问级别散落于设置与输入框角落 | 输入框聚合选择器（模型、访问级别、项目、附件） |
| 迁移路径 | 首次引导面向全新手 | 增加面向迁移用户的标准模式默认路径 + 会话导入器 |
| 插件面 | 插槽体系（不变） | 不变；插件内容经插槽进入标准模式 |

## 7. 演进路线（各片独立立项、独立验收）

| 阶段 | 内容 | 验收要点 |
|---|---|---|
| W1 | 标准模式交互壳：会话列表侧栏 + 布局切换持久化 + 形态开关 | 双形态会话状态一致；切换零数据丢失；桌宠常驻可达；纯前端改造，后端契约零变更 |
| W2 | 模式选择器 + 任务中心：输入框聚合选择器；定时能力统一只读视图 | 选择器触点全部可达；任务中心与各调度源状态一致（只读透传不重造调度） |
| W3 | 项目上下文 + 迁移设施：会话绑定项目、推断转显式、首个会话导入器 | 项目聚合三方资产一致性；导入器逐家适配并附许可与格式说明；快捷键约定测试 |

排序原则：W1 是壳，先行且风险最低（纯 UI 组合）；W2/W3 在壳上长内容；任何一片停滞不影响已落地片。

## 8. 受影响模块与契约面（终态视图）

- `packages/ui`：标准模式布局组件、会话列表、任务中心、模式选择器（增量全部为自有组件组合）；`useWorkbenchLayout` 增加形态状态；
- `packages/api-client`：会话列表/重命名/分组、任务计划只读查询、项目聚合查询的组合式封装（后端端点大多既有，缺口小步补齐）；
- `apps/api`：会话分组/置顶等轻量端点、项目聚合查询（衔接学习/收藏/主动 projects）；计划类只读聚合端点；
- 插件面：零契约变更——插槽体系原样进入标准模式。

## 9. 范围外

- 编码代理能力（终端执行、仓库级 agentic coding、diff 工作流）；
- 引入第三方聊天前端替换自有对话栈；
- 移动端形态调整（mobile 端另行评估）；
- 会话云同步与多设备（local_only 边界不变）；
- 主动智能调度语义的任何改动（任务中心只读透传）。

## 10. 安全、隐私与信任影响

- 会话分组与项目的全部数据仍在本机 SQLite（CR-030 边界不变）；
- 完全访问级别在选择器中前置可见，与既有 toolApprovalMode 语义一致，不新增隐式提权；
- 导入器处理外部导出文件：解析面视为不可信输入（体积上限、字段白名单、注入内容按记忆条目既有净化规则处理）；
- 双形态共享同一安全门禁（危机分类器、工具审批卡），不存在「标准模式绕过安全面」的旁路。

## 11. 风险、成本、灰度与回滚

| 风险 | 缓解 |
|---|---|
| 双形态维护成本翻倍 | 壳与内容分离：两形态共用全部业务组合式与回合管线，差异收敛在布局层；W1 落地后以组件级测试锁住共享面 |
| 任务中心重造调度语义的诱惑 | 范围声明「只读透传 + 跳转」，写入一律回各源分区 |
| 项目上下文与主动 projects 概念混淆 | 明确「推断是候选、确认是项目」的单向流，术语表同步 |
| 导入器适配面无底洞 | 首版只选一家主流格式，逐家立项；解析面按不可信输入处理 |
| 陪伴定位被稀释的舆论风险 | 标准模式是可选形态、桌宠常驻、默认路径可配置——扩大入口而非替换灵魂 |

回滚原则：W1/W2/W3 均为纯前端增量 + 轻量只读端点，形态切换开关可整体回退；无破坏性 schema 变更。

## 12. 与既有基线的关系（差量单声明）

- 对 **CR-032**：插件插槽体系原样承载于标准模式，主动事件双形态一致送达，零契约变更；
- 对 **CR-033**：标准模式是主动智能（任务中心、主动动态卡）的呈现面之一；P4 干预预算、态势投影不因形态改变；
- 对 **CR-034 本地模型降级阶梯（提案中）**：模式选择器中的模型标识拟消费其降级层级契约（本地模型 · 降级中），单向依赖；#192 合入后补正式链接；
- 对 **CAP-019/013/026**：桌宠常驻、回合管线、知识库衔接均继承；CAP-026 仅作 W3 项目资产的衔接预留，不提前实现。

后续 W1/W2/W3 立项时以本 CR 为引用基线，各自携带实现级契约与验收细节。
