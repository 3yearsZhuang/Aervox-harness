# ADR-011 日记周期、计划修订与连续窗口

- 提出人：3yearszhuang · 2026-08-26
- 修改人：3yearszhuang · 2026-08-31

- 状态：Proposed
- 日期：2026-08-24
- 关联：`CAP-009`、`FR-DIA-001`、`DATA-DIA-001`、`NFR-JOB-001`、`NFR-I18N-001`、`OPS-QUEUE-001`、`RISK-004/005`、`ADR-013`

> 更新日期：2026-08-31

## Context

AI 每日日记同时具有三类约束：

1. 用户看到的是“每个本地日期标签最多一篇自动日记”；
2. 日记素材必须按连续滚动窗口处理，不能因生成时间、时区、DST、停机或重试而重叠或出现未解释空洞；
3. Worker、Redis 和模型供应商均按至少一次语义运行，计划修改时还可能存在旧 Job、正在执行的 Job 和新计划并发。

仅使用 `localDate` 作为任务身份无法表达这些约束。例如用户在当天 00:30 已生成日记，随后把计划改为 22:00，新的截止点仍可能落在同一个 `localDate`；如果创建第二篇会违反产品唯一性，如果覆盖原文会破坏版本和用户编辑，如果直接推进到下一天又必须明确这段较长窗口的含义。

可变的 `DiarySchedule` 加一个整数 `version` 也不足以复现历史计划；`Diary`、`DiaryRun` 和 Schedule 同时保存窗口字段则会形成多个潜在真源。

## Decision drivers

- 一个获授权事件最多自动归属一个滚动周期；任何未覆盖区间必须有显式原因；
- 重复投递、进程崩溃和计划变更不能产生第二个已提交业务结果；
- 每个历史周期必须可复现当时的时区、权限、来源范围和计划版本；
- 保持“每个工作区、用户、本地日期标签最多一篇自动日记”的产品承诺；
- 日记关闭、撤权、失败和错过执行不能被静默折叠成普通成功；
- Redis/BullMQ 不是计划或 cursor 的事实源。

## Considered options

1. **以 `localDate` 作为任务和日记的共同身份**：简单，但计划/时区变更会产生同日碰撞，无法表达多个运行尝试或显式跳过。
2. **可变 Schedule + 每用户 Cron**：实现直观，但难以审计历史配置，进程重启、集群并发和 DST 行为不稳定。
3. **固定 24 小时 UTC 窗口**：避免 DST 计算，但不符合用户本地生成时间，也会让日期标签与素材窗口脱节。
4. **同一日期发生第二个截止点时自动覆盖或合并已有日记**：可以保留每日一篇，但可能覆盖用户编辑，且合并结果与周期状态难以幂等。
5. **不可变计划修订 + DiaryCycle cursor 链**：把调度事实、执行尝试和用户可见日记分开，以显式规则处理日期碰撞和排除区间。

选择方案 5。

## Decision

### 1. 数据所有权和身份

- `DiarySchedule` 是 `(workspaceId, subjectUserId)` 范围内的稳定身份；产品当前每个工作区/数据主体只能有一个自动日记 Schedule（数据库 `UNIQUE(workspaceId,subjectUserId)`），只保存启停状态和 `currentEpochId`，不保存可变配置正文。
- 每次首次启用或重新启用均创建 `DiaryScheduleEpoch`。Epoch 至少记录 `workspaceId/subjectUserId/scheduleId/epochId`、`startedAt/endedAt`、启用时的 consent/permission epoch，以及 `lastCycleId/lastCutoffAt/lastCoverageAt/cursorVersion`；所有 cursor 都在 epoch 内解释，不能把停用前 predecessor 接到重启后的首 Cycle。
- 每次启用、修改生成时间、修改时区、修改范围或关闭后重开，均创建不可变 `DiaryScheduleRevision`。Revision 至少记录：
  - `workspaceId`、`subjectUserId`、`scheduleId`、`revision`、`effectiveAt`；
  - 本地墙钟时间、IANA 时区、内容 scopes、宽限期和通知/免打扰设置；
  - 计算运行时或 tzdata 版本；
  - 创建 actor、同意版本和撤销状态。
- `DiaryCycle` 是滚动窗口的唯一事实源。每个 Cycle 至少记录：
  - `workspaceId`、`subjectUserId`、`scheduleId`、`epochId`、`scheduleRevisionId`、`predecessorCycleId`；
  - `windowStartAt`、`cutoffAt`（含）、`bufferClosedAt`；区间是否包含下界由 `lowerBoundInclusive` 决定；
  - `lowerBoundInclusive`（首次启用或重新启用的首周期为 `true`，普通周期为 `false`）、`localDateLabel`、IANA 时区、截止点 UTC offset、DST fold/gap 处理结果；
  - 状态、lease、fencing token、当前 Diary/运行结果引用。
- `DiaryRunAttempt` 记录一次 Worker/模型执行，显式带 `workspaceId/subjectUserId/cycleId`。重试创建新的 Attempt，但不创建新的 Cycle。
- `Diary` 只拥有用户可见叙事和版本；必须与 Cycle 使用同一 `(workspaceId,subjectUserId)` 复合外键，窗口字段来自关联 Cycle，不再独立成为 cursor 真源。
- `DiaryMaterialBuffer`、`LateMaterial`、`ExcludedInterval`、`SuppressedCandidate` 必须显式带 `workspaceId/subjectUserId` 并关联同数据主体的 `cycleId`/`scheduleId`；需要参与时间分区的 `ExcludedInterval` 还记录明确的 range bounds，不能仅依赖 `localDate` 或全局 UUID。组织操作者另记 `actorId`，不得作为日记主体。
- 所有上述子实体启用并 `FORCE RLS`；复合 FK 校验 workspace、user、schedule/cycle 的同属关系。Scheduler 只能通过受限 claim 函数领取工作，不能以 `BYPASSRLS` 读取日记正文或 Buffer。
- `OutboxEvent.workspaceId` 必须由聚合根的复合归属派生，禁止信任 Job payload；组织管理员默认不能读取成员 Diary、Buffer、LateMaterial 或来源快照，只能访问获批准的聚合字段。

### 2. 周期和日期唯一性

- Cycle 的业务唯一键是 `(scheduleId, epochId, cutoffAt)`；同一 Schedule/epoch 的有效 Cycle 时间范围不得重叠。非首 Cycle 必须满足 `windowStartAt = predecessorCycle.cutoffAt`，且 predecessor 属于同一 workspace、subjectUser、schedule、epoch；一个 predecessor 最多一个有效 successor。数据库至少实施 `CHECK(windowStartAt < cutoffAt AND cutoffAt <= bufferClosedAt)`，并以 `tstzrange(windowStartAt, cutoffAt, CASE WHEN lowerBoundInclusive THEN '[]' ELSE '(]' END)` 生成 `coverageRange` 参与排除约束；`Cancelled`/`LegacyUnverified` 不参与有效窗口约束。Epoch 保存 `lastCycleId + lastCutoffAt + lastCoverageAt + cursorVersion`，不能只保存时间戳。
- 自动 Diary 继续使用 SQLite 条件唯一索引：`(workspaceId, subjectUserId, localDateLabel) WHERE autoGenerated = true`。
- 为避免同日第二个截止点与 Diary 唯一性冲突，下一截止点必须同时满足：
  1. UTC 时点严格晚于当前 cursor；
  2. 在生效 Revision 的本地规则下，是合法计划时点；
  3. `localDateLabel` 严格晚于最近已终结自动周期的日期标签。
- 因计划或时区变更出现同一日期内的第二个候选时点时，记录 `SuppressedCandidate` 调度审计记录，不创建 `Skipped Cycle`，也不推进 cursor；下一个 Cycle 仍从上一 cursor 开始，因此会形成一个较长但连续的窗口。设置界面应预览下一截止点和预计窗口长度。
- `SuppressedCandidate` 只记录候选 cutoff、revision、抑制原因和 actor，不占用 Cycle 窗口、不推进 `lastCutoffAt/lastCoverageAt`，也不能被误读为用户放弃了真实窗口。
- 不允许通过创建同日第二个自动 Diary、覆盖用户编辑或把 `scheduleVersion` 加入 Diary 唯一键来绕过该规则。

### 3. Cursor 与状态机

Cycle 状态机为：

```text
Planned
  -> Claimed
  -> Generating
  -> Validating
  -> Published

Planned/Claimed/Generating/Validating
  -> RetryableFailed -> Claimed
  -> TerminalFailed
  -> Cancelled

RetryableFailed/TerminalFailed/Cancelled
  -> Claimed (explicit retry after authorization recheck)

Planned/RetryableFailed/TerminalFailed/Cancelled
  -> Skipped
```

不变量：

1. 在同一授权 epoch 内，只有 `Published` 和显式 `Skipped` 会推进该 Epoch 的 `lastCutoffAt` 与 `lastCoverageAt`；失败、取消、`SuppressedCandidate` 和过期 lease 不推进。关闭尾段由 `ExcludedInterval` 单独推进 `lastCoverageAt`，不推进 `lastCutoffAt`。
2. `Published/Skipped`、Cycle 终态、Diary 引用、cursor 更新和 Outbox 必须在同一 SQLite 事务提交；`ExcludedInterval`、epoch 关闭和 coverage cursor 更新也必须原子提交。
3. 提交事务必须比较预期 `epochId`、`lastCycleId`、`cursorVersion`、Cycle 冻结的 `scheduleRevisionId`、consent/permission epoch 和 fencing token；任一不匹配时保持 Cycle 不变，将 Attempt 标记 `StaleRejected/Superseded` 并写 AuditRecord，不能让旧 Worker 改写当前状态。撤权控制事件必须先按 ADR-013 获得独立账本 durable ack；本地授权投影水位未追平时禁止 claim、读取 Buffer 或发布。
4. 一个 Schedule 同时最多有一个会推进 cursor 的非终态 Cycle。后台可以预计算后续候选，但不能提前提交其窗口。
5. Worker lease 到期可重新领取；旧 Worker 即使稍后返回模型结果，也不能越过 fencing token 提交。
6. 如果供应商调用已发生但提交前崩溃，可能产生重复供应商费用；系统保证业务结果不重复，并将重复 Attempt 记录为可观测成本事件。

`Skipped` 必须有原因和 actor，例如用户主动跳过、明确选择不补写、运维批准放弃无法恢复的历史周期。系统不能为了让后续任务继续而静默跳过。

### 4. 计划修改、关闭和错过执行

- Revision 修改不改变已经 `Claimed` 或更后阶段 Cycle 的窗口；新 Revision 在同一 epoch 的下一 Cycle 生效。
- `Planned` Cycle 是唯一允许重算窗口的阶段。计划修改时，以 expected state/revision CAS 原子更新同一 Planned 行的 `scheduleRevisionId`、窗口、日期标签和 DST 解析结果，并把旧值写入 AuditRecord；一旦进入 `Claimed`，窗口字段永久冻结。不得创建 `Superseded` 替代 Cycle 来绕过 `(scheduleId,epochId,cutoffAt)` 唯一键；重算后的 `windowStartAt` 必须等于当前 Epoch 的 coverage cursor，若新 cutoff 与既有 Cycle 冲突则拒绝提交并重新规划。
- 首次启用默认 `initialWindowStart = enablementCommittedAt`。回溯历史必须是单独、显式授权且有上限的操作，不能作为默认启用行为。
- 关闭或撤销日记同意后，未执行 Job 和 Buffer 立即失效。`disabledAt` 是第一个无权进入日记的时点：关闭事务以明确 bounds 记录旧 Epoch 尚未覆盖的尾段 `(lastCoverageAt, disabledAt)`，把旧 Epoch `lastCoverageAt` 推进到关闭边界并结束该 Epoch；`lastCutoffAt` 不变。若区间为空则只记录 epoch 结束审计，不制造零长度范围。
- 重新启用事务把关闭区间记录为 `[disabledAt, reenabledAt)` 的 `ExcludedInterval`，再创建新的授权 Epoch，并令其初始 `lastCoverageAt=reenabledAt`、`lastCutoffAt/lastCycleId=null`。首个重启 Cycle 的 predecessor 为空并使用 `[reenabledAt, cutoffAt]`，普通 Cycle 使用 `(previousCutoffAt, cutoffAt]`。这样 `disabledAt` 及之后的来源都不会被旧授权读取，`reenabledAt` 恰好发生的来源只归属新 Epoch。用户若选择回溯关闭期间，必须重新确认范围和来源权限，并进入独立历史回顾流程。
- Scheduler/队列停机后按 cursor 顺序重建逾期 Cycle，不把多个计划周期静默合并成一个巨大周期。自动补跑数量使用已批准的 `maxCatchUpCycles`；超过上限的周期进入用户/运维可见的待处理状态，只能显式补跑或跳过。
- quiet hours 只延迟通知，不改变 `cutoffAt`、生成任务或 15 分钟发布 SLO。

### 5. 时区与 DST

- Schedule 使用 IANA 时区和本地墙钟规则计算候选时点，不能使用固定 24 小时间隔。
- DST 缺口选择缺口后的第一个合法时点；DST 重叠默认选择较早的 occurrence。实际选择、offset 和 resolved UTC 必须写入 Cycle。
- 修改时区使用新 Schedule Revision；已经生成的 Cycle 永远使用自身快照，不被后续 tzdata 或偏好修改重算。
- `localDateLabel` 只是展示/唯一性标签；完整性判断以 UTC cursor 链为准，不以“每天恰有一个标签”推断无空洞。

### 6. 素材事件时间和迟到规则

每个可用于日记的来源必须有：

- `occurredAt`：按该来源类型定义的业务发生时间；
- `ingestedAt`：进入 Aervox 事实库的提交时间；
- 不可变来源版本和权限状态。

归属规则：

1. 普通 Cycle 只有 `windowStartAt < occurredAt <= cutoffAt` 的来源属于该 Cycle；首个启用/重启 Cycle 若 `lowerBoundInclusive=true`，则使用 `windowStartAt <= occurredAt <= cutoffAt`。
2. 生成冻结前已入库的合格来源进入初始版本。
3. `cutoffAt < ingestedAt <= bufferClosedAt` 且事件时间仍落在该 Cycle 的来源，只形成该 Cycle 的补写候选；用户确认后创建新 DiaryVersion。
4. `occurredAt > cutoffAt` 的来源自然进入后续 Cycle。
5. `occurredAt <= windowStartAt` 或在宽限期后才到达的历史来源，不得伪装成下一 Cycle 的事件。它进入 `LateMaterial`，由用户选择关联历史日记、建立手动补记或忽略。
6. 外部历史导入默认以用户确认/导入时间作为“当日日记发生时间”；若要按历史业务时间生成回顾，应进入独立的历史回顾流程，不能污染每日 cursor。

Buffer 只保存来源引用和获单独授权的最小临时快照。撤权或来源删除立即使其不可用；清理任务必须有 TTL、幂等状态和积压告警。

## Positive consequences

- 计划修改、时区、DST、重复任务和宕机均能由同一 cursor 模型解释；
- 日记业务唯一性与运行尝试解耦，不再靠 `localDate + scheduleVersion` 制造分片；
- 可以通过数据库不变量和性质测试证明无重叠、无未解释空洞；
- 失败、跳过、关闭和迟到均可见且可审计；
- Redis 丢失后可完全从 SQLite Schedule/Cycle/Outbox 重建。

## Negative consequences and risks

- 增加 ScheduleRevision、Cycle、Attempt、ExcludedInterval/LateMaterial 等实体和状态迁移；
- 为保持每日一篇，某些计划/时区修改会产生较长窗口，需在 UI 中解释；
- 至少一次供应商调用无法保证零重复费用，只能保证单一提交结果；
- 时区数据库升级和跨日期线测试成本增加；
- TerminalFailed 会阻塞后续 cursor，需要明确的用户/运维处置和告警。

## Migration / rollback

- 在没有生产数据时直接按新模型实现，不先发布仅以 `localDate` 为调度真源的临时方案。
- 若已有 Diary 数据，按其已记录窗口创建只读历史 Cycle；无法证明窗口的记录标为 `LegacyUnverified`，不能自动参与补写或 cursor 推导。
- 新 Scheduler 通过 Feature Flag 灰度；切回旧版本时停止领取新 Cycle，但不得回退 `lastCutoffAt`、删除 Cycle 或重建同日第二篇日记。
- Schema 使用 expand/contract：先双读验证新投影，确认一致后停止旧字段写入，最后再清理冗余字段。

## Verification evidence

状态改为 `Accepted` 前至少提供：

- SQLite 条件唯一约束、cursor CAS 和 fencing 集成测试；
- 性质测试分别证明首 Cycle 的 `[windowStartAt, cutoffAt]` 与普通 Cycle 的 `(windowStartAt, cutoffAt]` 两两不重叠，且 Cycle/ExcludedInterval 按 bounds 构成无未解释空洞的 coverage 链；
- 00:30→22:00、22:00→00:30、下一运行前多次修改、跨午夜和跨国际日期线测试；
- DST gap/fold、tzdata 升级和 resolved UTC 回放测试；
- 重复 Job、lease 过期、旧 Worker 晚返回、模型成功后数据库提交失败和 Redis 全丢失测试；
- 首次启用和重开时点精确边界、关闭尾段/关闭区间、撤权与 Published 提交竞态、空日记、显式跳过、TerminalFailed 和多日停机补跑测试；
- 跨 workspace 复合 FK、同 workspace 不同用户和组织管理员 RLS、Scheduler/Worker 最小权限测试；
- 两个并发首 Cycle、predecessor 分叉、同 cutoff Planned 重算、`SuppressedCandidate` 不推进任何 cursor 的竞态测试；
- 宽限期内迟到、宽限期后迟到、早于窗口下界和历史外部导入测试；
- 指标和告警覆盖 cursor 停滞、重叠拒绝、同日碰撞、逾期周期、重复供应商调用、Buffer 过期和 DLQ。
