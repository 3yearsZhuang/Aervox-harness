# ADR-006 AI 召回期限与历史保留期限分离

- 提出人：3yearszhuang · 2026-08-26
- 修改人：3yearszhuang · 2026-08-31

- 状态：Proposed
- 日期：2026-08-23
- 关联：`CAP-005/009/013`、`PRIV-RET-001`、`NFR-PRIV-001`

> 更新日期：2026-08-31

## Context

临时记忆默认 6 小时后不应自动进入模型上下文，但用户可能仍有查看、导出和删除聊天历史的权利。把数据库 TTL 当成召回 TTL 会导致不可接受的数据权利冲突。

## Decision drivers

- 用户查看/导出/删除历史与 AI 不再召回是两套权利，不能混用同一 TTL；
- “看不到就删掉”会成为隐式承诺，违反数据控制原则；
- 删除请求必须即时 deny，异步清理与召回停止分离。

## Considered options

1. **`aiRecallUntil` 与 `userRetentionUntil` 分离**：两套期限独立演进（选定）。
2. **单一 TTL 复用**：实现简单，但会错误地把用户历史保留与模型召回绑死。
3. **永久保留一切**：符合数据控制，但超出隐私最小化与成本约束。

## Decision

分别存储 `aiRecallUntil` 和 `userRetentionUntil`。召回到期只改变 Context Builder 和索引资格；历史保留由用途/地区/用户设置决定。删除请求立即 deny，随后清理派生数据、缓存、对象和供应商副本。

## Positive consequences

- 满足连续性（6 小时内可召回）与用户控制（历史长期可见）分离；
- 避免“看不到就删掉”的隐式承诺；
- 删除语义清晰：召回到期 ≠ 历史删除。

## Negative consequences and risks

- 需要维护两套状态、UI 解释和删除测试；
- 配置错误时可能误删历史或延长召回，需要默认保守策略。

## Migration / rollback

旧单 TTL 数据迁移为明确的来源/召回/保留字段，未知值进入最保守策略；迁移可回滚且不恢复已删除内容。

## Verification evidence

状态改为 `Accepted` 前至少提供：

- 召回到期仍可历史查看、用户提前禁用召回的测试（`TC-PRIV-RET-001`）；
- 来源删除后零召回（`TC-PRIV-DEL-001`）；
- 备份恢复重放删除账本（`TC-RES-LEDGER-001`）。

## 验收差距复核（2026-08-31）

- **未满足**：`TC-PRIV-RET-001`（召回到期可历史查看/提前禁用）、召回侧删除零召回与 `TC-RES-LEDGER-001` 备份重放演练均未自动化。
- **推进路径**：召回/保留功能批次补自动化后走 G2 评审。
