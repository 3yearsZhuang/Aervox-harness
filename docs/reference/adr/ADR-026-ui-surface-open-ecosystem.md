# ADR-026 界面插件开放生态与安装回滚（提案）

<a id="cr-064"></a>

## 1. 背景与问题

CR-065（已 Implemented）把根界面与设置面板改造成"受信构建输入"的第一方 UI 插件：`UISurfaceManifest` 描述符、`@aervox/ui-host` 装配校验、组合根显式选择均已落地，但明确排除了两类开放能力：

1. **第三方 UI 插件**：社区开发者编写的根界面 / 面板 / 桌宠皮肤，代码来源不受信；
2. **界面插件独立安装与升级回滚**：UI 插件脱离应用发版节奏，单独分发、安装、升级与回滚。

当前 `UISurfacePlugin.load()` 直接执行构建期代码，宿主只做清单校验，没有任何针对不受信代码的隔离、配额或回滚语义。本提案为这两个开放动作建立前置合同，未批准前维持"仅受信构建输入"现状。

## 2. 决策与范围（待评审）

### 2.1 第三方 UI 插件信任模型

- **信任分级**：L0 内置受信（现状第一方）→ L1 签名社区插件（发布者签名 + 哈希锁定）→ L2 未签名本地插件（默认禁用，显式授权后启用）。
- **能力白名单**：第三方界面插件运行于受限上下文中——禁止直接 `fetch`/`XMLHttpRequest`（网络只经 `@aervox/api-client` 受限面）、禁止 `localStorage` 直写（经命名空间化 `pluginState`）、禁止动态 `import()` 远程 URL；DOM 范围限定于宿主分配的挂载点。
- **隔离与降级**：渲染异常由宿主意面错误边界隔离并自动回退到内置默认界面；不因第三方代码崩溃带走会话数据。
- **撤销语义**：禁用/卸载即时生效，下一装配周期不再加载，残留配置与数据保留（沿用 CR-030 数据权利口径）。

### 2.2 界面插件独立安装、升级与回滚

- **分发形态**：复用 `.aervox-plugin` 声明式分发的打包与预检管线，但扩展清单类型为 `ui-surface`（区别于业务插件 manifest），包含目标插槽（main/companion/panel）、兼容宿主 API 版本区间、签名与内容哈希。
- **版本协商**：宿主按 `requires.hostApiVersion` 区间与平台清单决定是否可安装；不满足即拒绝并保留旧版。
- **回滚合同**：每次升级保留上一份可用包；新版本首次加载失败或 24h 内连续崩溃达阈值即自动回退内置界面并提示用户；回滚不删除用户数据。
- **来源校验**：安装前校验签名（L1）与解压配额；SHA-256 字节可重现性沿用现有分发包门禁。

### 2.3 非范围

- 不改变第一方 UI 插件（workbench-ui / companion-ui / panels-ui）的现有装配链；
- 不引入远程代码热更新通道（无网络下发执行代码）；
- 原生移动真机验收沿用 CR-055 / ITER-009 既有条目，不在本提案内扩张；
- 第三方插件的服务端能力（工具/路由贡献）已有 CR-060 体系，本提案只覆盖界面层。

## 3. 验证与回滚（实施后适用）

- 信任分级：未签名插件默认拒绝加载；签名篡改、哈希不匹配、能力越界调用各有负向测试；
- 安装/升级/回滚：完整生命周期演练（安装 L1 插件 → 升级 → 新版崩溃 → 自动回退内置界面 → 数据完好）；
- 兼容矩阵：宿主 API 版本升降级与插件声明区间的接受/拒绝表；
- 性能配额：第三方界面加载计时与包体上限，超时/超限拒绝；
- 回滚本提案本身：未实施前无代码变更；实施后回退即恢复"仅受信构建输入"。

## 4. 待评审问题

1. 签名基础设施：是否引入发布者公钥目录，还是只做内容哈希锁定？
2. L2 未签名插件是否允许存在于正式发行版，还是仅限开发者模式？
3. 界面插件崩溃阈值的自动回退策略是否同样适用于第一方界面？
4. `ui-surface` 类型分发包是否进入插件市场列表（只读展示 vs 可一键安装）？
