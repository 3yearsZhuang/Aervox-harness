## 1. 目标与不变量

可选功能模块化方案回答一个问题：**非核心能力如何既以独立代码库参与开发，又能被主仓以 workspace 包方式消费、并按构建/运行时两轮对用户可自选启用。**

本方案的不变量（违反任一即需先停止并走 `CR-*`）：

1. **可选 ≠ 核心可丢**。P0（CAP-001~013）是学习/陪伴闭环的必要能力，始终在主仓普通包中，不进入自选机制；自选只影响非核心体验与扩展，不改变核心闭环、安全、隐私、删除与导出承诺。
2. **可选功能只用子仓库开发**。任何被判定为可选的非核心功能，其代码必须位于独立 git 仓库并经 git submodule 挂入 monorepo 后消费，禁止在主仓 `packages/` 内另起"可选却在主仓开发"的平行实现。
3. **消费一律走 workspace 包**。子模块目录在 pnpm workspace 中即成为包（`@aervox/mod-*`），主 app 通过 `workspace:^` 依赖，不通过路径 hack 或复制代码引用。
4. **单一事实源不分裂**。可选模块的接口必须输出之一：
   - OpenAPI / 事件 schema（走 `packages/contracts` 或模块自带 schema，二选一并登记）；
   - 或 TypeScript 类型 + 契约文档（AVX-MOD 注册）。
   不得为同一功能在模块与主仓维护两套互相漂移的接口定义。
5. **默认不启用**。可选功能不进入默认构建产物；启用才产生依赖与运行时成本。

## 2. 机制定义

### 2.1 目录与归属

| 目录 | 性质 | 说明 |
|---|---|---|
| `reference/*` | git submodule，只读设计参考 | 版本锁定、不参与构建，仅借鉴思想（现已有 deepseek-harness/pi/baishou-next/dsh-synapse） |
| `modules/*` | git submodule，可选功能载体 | 本次新增；每个子模块是独立开发仓库，作为功能代码的事实源 |
| `packages/contracts` | 主仓契约 | 与共享/跨模块相关的 OpenAPI/schema，可选模块可引用 |
| `packages/*`、`apps/*` | 主仓普通包 | 核心功能；可选模块的优秀产物也归入模块，不搬回主仓 |

### 2.2 workspace 纳入

`pnpm-workspace.yaml` 需在现有基础上追加 `modules/*`（本方案为规划，落地时执行）：

```yaml
packages:
  - "apps/*"
  - "packages/*"
  - "modules/*"
```

新增可选功能模块的注册约定：`modules/<name>/package.json` 中 `name` 统一为 `@aervox/mod-<name>`；主 app 通过该 workspace 名依赖。

### 2.3 两轮自选（构建 + 运行时）

自选在两个粒度上分开控制，二者可同时存在（双机制）：

#### A. 构建时自选（发布/打包时决定默认集）

- 主仓通过 workspace 依赖与构建配置决定"默认打包哪些可选模块"；
- 未在默认列表的可选模块不进入产物，减少体积与攻击面；
- 用于：桌面端（CAP-018）、Live2D / 桌宠皮肤、本地优先（CAP-027）等在发布边界上更自然的候选。

#### B. 运行时自选（端用户在设置里开关）

- 已打包进产物的可选功能在运行时按用户配置启用/停用；
- 运行时开关只影响"功能是否可被触发"，不影响已存在数据、安全与删除边界；
- 用于：插件系统（CAP-020）、第三方接入、知识库/收藏项等以"安装/授权/开关"为交互形态的候选。

> 二者关系：构建时决定**能力是否存在**，运行时决定**对当前用户是否可用**。一个可选功能必须至少落入其一，声明于 [第 4 节](#4-可选功能清单)。

### 2.4 版本锁定与升级

- 每个 `modules/*` 子模块固定 commit / tag；升级需走 `CR-*` 并记录变更原因、依赖画廊（peer 版本）与回归结果（对齐 `PRD 15.1` 的参考仓库规则）。
- 主仓记录各模块的"已批准版本"，作为构建清单事实源；升级前在 CI 中跑模块自身测试 + 主仓集成测试。

### 2.5 接口边界

- 可选模块不得拥有 Aervox 核心业务数据的直接写入权；需要读写学习/记忆/日记时，只能使用主仓暴露的受限接口或提交"候选"，由主仓领域规则决定最终落库（对齐 `PRD 14.3` 的 dsh/pi/MCP 接线约束）。
- 模块输出的数据生命周期（召回、保留、删除、导出）仍服从主仓 `DATA_PRIVACY`，模块不得自建独立的删除/同意旁路。

## 3. 核心 / 可选边界判定准则

判定一个功能"是否可选"用以下四条正向条件，**全部满足**才纳入本机制：

1. **不构成闭环必要条件**：移除后核心"目标→引导→练习→复习→记忆"闭环仍完整成立；
2. **存在清晰接口边界**：可用适配器/包级接口与主仓隔离，不依赖修改核心领域实体代码；
3. **启用/停用可撤销且无数据破坏**：开关不破坏已保存数据，可回滚；
4. **独立版本化有意义**：该能力可单独演进、单独发布或单独授权。

**反向检查（防误伤）**：尽管某些期望/表现可被伪装成"可选"（例如桌宠形象 CAP-001 的表现层、NFR 的无障碍/性能），凡是承担学习闭环、安全、隐私、删除/导出、或学习事实真源的功能，**一律保留主仓**，不因"看起来像皮肤"而纳入自选。

> 决策边界：把某个 P0 判定为"可选"（即使表现层）属不可逆架构决策，必须新增 ADR；P1/P2/P3 纳入本机制不改变其增长路线，只改变其交付载体。

## 5. 生命周期与门禁

1. **新增可选模块**：先走 `CR-*` 在追踪矩阵登记新模块与受影响 CAP → 建立独立 git 仓库 + 固定版本 → 以 submodule 挂入 `modules/*` → 声明进入 [第 4 节]清单（状态/启用方式/接口边界/关联 ADR）→ 更新 docs/README 登记表与构建清单。具体命令与两层提交规范见[协作指南](../how-to/submodule-collaboration.md)。
2. **CI**：可选模块自身 CI（build/typecheck/test/OpenAPI diff）+ 主仓集成 CI（引用改动时跑）。`ci.yml` 需纳入 `modules/*`；未初始化的 submodule 应让 CI 失败而非静默跳过。
3. **许可证 / 安全检查**：每个可选模块按其来源执行许可证评审（align `PRD 15.1`），AGPL 类模块不得形成主仓链接依赖。
4. **数据 / 隐私 / 删除**：模块不得绕过主仓删除、同意、导出与保留边界（见 [2.5]）。
5. **回滚 / 降级**：任一可选模块构建或运行时降级，不阻断核心流程；被禁用的模块数据按主仓删除/导出规则处理。
6. **更新登记**：模块每次批准/修订后更新本文档与[文档索引登记表](../README.md#11-文档生命周期登记表owner-指派与核验)的核验日期。

## 6. 风险与替代方案

| 风险 | 缓解 |
|---|---|
| **git submodule 用于运行时功能被普遍视为反模式** | 本方案把 submodule 仅作为"开发代码来源 + 版本锁定"，消费一律走 pnpm workspace 包；运行时开关由主仓构建/配置表驱动，不在运行时动态拉取 submodule |
| 子模块未初始化 / commit 漂移导致构建假绿或失败 | CI 显式校验 `modules/*` 初始化与 pin；未 pin 视为失败 |
| 可选功能私自读写核心数据 | [2.5] 强制受限接口/候选制，字段级来源约束 |
| "可选"被滥用为绕过 P0 责任 | [3] 反向检查把安全/闭环/隐私规定为核心不选，误判需新 ADR |
| 生态与插件系统（CAP-020）与"可选模块"演化重叠 | 本方案提供**构建时**载体（`@aervox/mod-*`），CAP-020 提供**运行时**插件运行与沙箱；两者未来可统一到插件宿主，本文档保留该演进路径 |

### 6.1 与现有 reference/ 的关系

`reference/` 是只读设计参考（不消费、不运行）；`modules/` 是可选功能运行载体（会被 workspace 消费）。二者不得混用：参考项要转可选功能时，先按其许可证评估，再另建独立 `modules/*` 仓库，不把 reference 直接提升为模块。
